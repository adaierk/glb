本次新增
1. 原 0x04 账号控制请求恢复完整发送：13 字节，body 是账号 ID（并非 SID）。
   执行原 0x620760 -> 0x61B090 -> 0x43D2C0 -> 0x60A3E0 -> 0x6098D0 -> 原传输封装。
   原控制器自然从阶段 7 进入阶段 8，原查询对象保存到 controller+0xCC。
2. 分离两个原通信通道及查询池：0x18 准入走 controller+8，0x04 控制走 controller+4。
   测试初始化两个独立 NNet 对象、注册表、包装器和查询池，分别执行原 bootstrap 与 sender。
   v7 等旧测试中的两个包装器曾共享同一测试对象；v8 新测试不再依赖该共享假设。
   通道名称仅描述原对象路径，不声称已经确认历史服务器端完整拓扑。
3. 原 0x11 header-only 答复（9 字节）可关联 0x04 请求并将阶段 8->9，result=2。
   请求号错误、答复到错查询池或 opcode 0x05 均保持阶段 8/result=1。
   使用真实原机器码设置查询状态与结果，没有手工写入成功状态。
   这是经原处理器验证的兼容答复，不证明已取得停服服务端当年的真实答复记录。
4. 本地服务端加入 0x04/0x11 处理。要求控制连接已通过账号登录或游戏登录，
   包内账号 ID 与已验证账号匹配，并存在唯一可绑定、未过期、角色仍存在的准入票据。
   两条 TCP 连接分别执行准入和控制消息。已绑定同一控制连接可重复答复；
   多个未绑定准入导致歧义时拒绝，不任意挑选角色。
5. 数据库票据表自动增加 attached_by 列，保留原账号与角色。
   准入或控制连接断开后对应票据失效。服务重启不复活旧连接票据。
6. Windows 只读探针增加 WORLD_CONTROLLER_COMPLETED_NATIVE，条件为真实原 worker
   阶段 8->9 且 result=2；runtime_result.json 增加 world_controller_completed。
   达到该原生事件后自动截图并记录到 screenshots.json。
   map_entered/playable 保持未知，不从阶段 9 推断进入地图。
